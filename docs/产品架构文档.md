## 1. 核心理念

### 1.1 愿景

长期来看，办公应该是**人和 Agent 在一起的**。每一个人都可以有几个 Agent 帮他做事情。

核心目标：
- 让用户的时间尽可能缩减在执行性工作上
- 更多的工作让 Agent 来做
- **用户只需要做决策**

### 1.2 产品本质

不是工具，是一个**替你跑的人**。

传统办公产品是**人操作工具**。这个产品是**人指挥 Agent，Agent 操作一切**。

核心体验不是"打开一个软件去干活"，而是"有一个一直在帮你跑的人，你只需要偶尔拍板"。

### 1.3 关键设计原则

1. **用户面对的不是一堆工具，是一个人** — 没有"文档工具""表格工具""邮件工具"的概念，只有 Agent 和 Context
2. **Agent 管执行，人管决策** — 出了错能撤回的 Agent 自己来，撤不回的推给人
3. **飞轮效应** — 用户每次决策都在训练 Boundary，Boundary 越完善，Agent 自主比例越高，用户需要做的事越少
4. **Her 的感觉** — 一个人，一个助手，工作和生活不割裂

## 2. 抽象实体模型

### 2.1 一级实体（6 个）

| 实体 | 职责 | 关键属性 |
|------|------|----------|
| **Human** | 决策者、意图发起者 | 身份、偏好、权限边界、时间可用性、决策风格、精力状态 |
| **Agent** | 执行者、建议者 | 能力域、信任等级、自主权范围、协作协议 |
| **Context** | 用户数据的统一视图 | 工作上下文 + 生活上下文，持续累积 |
| **Intent** | 一条待完成的事 | 来源（人/Agent/环境触发）、优先级、状态机 |
| **Action** | 一次具体操作 | 执行者（人/Agent）、影响范围、可逆性 |
| **Boundary** | 协作的规则与边界 | 什么能自动做、什么必须人确认、隐私边界 |

### 2.2 Human

不只是一个账户，而是带**偏好模型**的决策主体。

关键不是"用户画像"，而是**决策风格**：哪些事愿意委托、哪些必须亲手过。

还有一个隐含属性：**精力状态** — 同一个人在不同时刻，委托意愿不同。

### 2.3 Agent

不是一个万能助手，而是**能力域明确的执行单元**。

每个 Agent 有：
- **能力域**（日程管理 / 信息检索 / 文档处理 / 沟通代发…）
- **信任等级**（0=只能建议，1=可执行可逆操作，2=可执行不可逆但需确认，3=完全自主）
- **协作协议**：跟其他 Agent 之间怎么协调，避免冲突

### 2.4 Context

这是最关键的实体。用户的全部数据统一在 Context 中：

```
Context
├── WorkContext
│   ├── 项目状态、文档、日程、沟通记录
│   ├── 任务链路（谁在做什么、卡在哪）
│   └── 组织关系（汇报线、协作网络）
├── LifeContext
│   ├── 日常习惯、健康数据、消费模式
│   └── 社交关系、兴趣偏好
└── CrossContext
    ├── 时间分配模式
    ├── 压力/负荷信号
    └── 长期目标与价值观
```

Context 的难点不是存储，是**感知** — 怎么低成本持续获取。解法方向：
- **被动采集**（邮件/日历/IM 自动聚合）
- **主动喂养**（用户碎片化输入）
- **环境推断**（位置、时间、行为模式）

### 2.5 Intent

人和 Agent 的交汇点，协作系统的核心枢纽。

```
Intent
├── source: human | agent | environment
├── urgency: now | today | this_week | someday
├── certainty: clear | fuzzy | unknown
├── delegation: auto | suggest | require_human
└── state: detected → planned → executing → done → reviewed
```

关键设计：**Intent 不区分是谁发起的**。Agent 发现日程冲突，自动产生一条 Intent；用户说"帮我订个餐厅"，也是一条 Intent。统一模型。

### 2.6 Action

执行单元：

```
Action
├── executor: human | agent:{id}
├── reversible: boolean
├── impact_scope: self | team | external
├── requires_approval: boolean (由 Boundary 决定)
└── result: outcome + feedback_to_context
```

每条 Action 执行完，结果**回流到 Context**，形成闭环。

### 2.7 Boundary

用户为什么愿意分享数据？因为**边界清晰、可控、可审计**。

```
Boundary
├── data_scope: agent 能看什么
├── action_scope: agent 能做什么
├── approval_rules: 什么情况下需要人确认
├── privacy_tier: 数据敏感度分级
└── audit_trail: 所有 agent 行为的可追溯记录
```

### 2.8 协作核心逻辑

```
环境信号/用户输入 → 产生 Intent
                        ↓
              delegation 判断
              ↙            ↘
      agent 自动执行     推荐给人
      (Action → Context)  (人决策 → Action → Context)
                              ↑
                        Boundary 兜底
```

- **什么时候 Agent 做：** 可逆 + 低影响 + 高确定性 + 在 Boundary 内
- **什么时候人做：** 不可逆 + 高影响 + 涉及关系/情感/价值判断
- **灰色地带：** Agent 做草案，人拍板

## 3. 交互原语设计

### 3.1 用户必须做的动作，只有三种

| 动作 | 对应实体 | 例子 |
|------|---------|------|
| **说** | Intent 产生 | "帮我订明天的会议室" |
| **选** | Boundary + Action 审批 | "Agent 帮你拟了回复，发不发？" |
| **划** | Context 喂养 + Boundary 设置 | "这个别碰" / "这块你可以自己搞" |

### 3.2 最简交互：一个对话框 + 一张卡片流

**对话框 — 处理"说"**

一个永远在的输入框。文本、语音、图片、链接，扔进去就行。

Agent 收到后做两件事之一：
- **能直接干的**：干了，结果变成一张卡片推回来
- **拿不准的**：也变成一张卡片推回来，等你选

**卡片流 — 处理"选"**

Agent 所有需要人介入的输出，都是一张卡片。关键：**每张卡片底部都有一个"以后这类事你自己来"的选项** — 这就是 Boundary 的渐进式建立。

**无交互 — 处理"划"的另一半**

用户不说话、不选的时候，系统也在工作。只有 Agent 拿不准时才推卡片。

### 3.3 不需要文件浏览器

文件夹、项目树、文件列表，本质上是**因为机器不够聪明，才需要人去组织和浏览的**。

用户不需要"浏览"，用户需要的是"看见当前"：

| 传统方案 | 新方案 |
|---------|--------|
| 打开文件夹找文件 | "上次跟老张聊的那个方案" |
| 打开项目看进度 | "XX 项目现在卡在哪儿" |
| 浏览最近文档 | "我今天该处理什么" |

用户偶尔需要看全局（Dashboard），但这不是文件浏览器，是 **Context 的可视化切片**。

## 4. 各场景协作模型

### 4.1 通用模式

所有场景就三种模式：

| 模式 | 适用场景 | 原则 |
|------|---------|------|
| **Agent 跑，人看结果** | 日程管理、会议纪要、数据查询 | 可逆 + 低风险 → Agent 全干 |
| **Agent 起草，人定稿** | 文档、邮件、消息回复 | 涉及表达 → Agent 出初稿，人改 |
| **Agent 催，人决策** | 审批、关键任务、对外沟通 | 涉及权责 → Agent 只提醒和准备 |

决策标准：**这件事出了错，后果能不能撤回？**

### 4.2 日程（Calendar）

```
Agent 主导：
├── 扫描所有日程，发现冲突 → 推卡片
├── "下周要跟老张开会" → Agent 去协调时间
├── 会前 10 分钟推材料摘要
└── 会后自动创建待办（从会议纪要提取）

人做决策：
├── 这个会要不要开 / 取不取消
├── 跟谁开 / 邀不邀请某人
└── 时间偏好（下午不想开会）

协作模式：Agent 编排，人拍板
```

### 4.3 文档（Docs / Wiki）

```
Agent 主导：
├── 找到相关文档（语义检索，不是关键词）
├── 生成初稿（基于 Context 里的素材）
├── 整理 / 总结 / 提取要点
├── 多文档合并、格式化
└── 按模板填充内容

人做决策：
├── 观点和判断（这是不是我们想要的方向）
├── 语气和立场调整
├── 审批发布 / 分享范围
└── 最终定稿

协作模式：Agent 起草，人定稿
```

### 4.4 即时消息（IM）

最敏感的场景。**消息代表关系，Agent 绝不能替你社交。**

```
Agent 主导：
├── 归类消息（重要/可以等等/垃圾）
├── 提取待办（"老张让你周五前给个反馈"）
├── 总结群消息（"这个群今天聊了什么"）
└── 起草回复（推卡片给你审）

人做决策：
├── 发不发这条消息（每条都要你确认）
├── 语气和措辞（关系是你的，不是 Agent 的）
└── 谁值得回复、谁可以忽略

协作模式：Agent 过滤+起草，人决定+发送
```

### 4.5 多维表格 / 数据（Bitable / Sheets）

```
Agent 主导：
├── 查询数据（"XX 项目进度怎么样"）
├── 生成报表和图表
├── 数据清洗和整理
├── 按规则批量更新记录
└── 异常检测（"这个数据不对劲"）

人做决策：
├── 数据模型设计（建什么表、什么字段）
├── 数据解读（这组数据说明什么问题）
├── 异常数据怎么处理
└── 基于数据的业务决策

协作模式：Agent 是数据分析师，你是决策者
```

### 4.6 邮件（Mail）

```
Agent 主导：
├── 归类 + 优先级排序
├── 长邮件摘要
├── 起草回复（推卡片）
├── 跟踪（"你答应周五给人反馈，要回了"）
└── 批量处理低优先级（归档 / 标记已读）

人做决策：
├── 重要邮件的回复策略
├── 敏感邮件的措辞
├── 是否需要转给其他人
└── 长期关系维护的判断

协作模式：Agent 过滤+起草，人审阅+发出
```

### 4.7 会议（Meeting / VC）

```
Agent 主导：
├── 会前：准备材料、拉取相关文档
├── 会中：实时记录、提取要点
├── 会后：自动生成纪要、提取待办
├── 跟踪：待办分配到人、提醒截止日期
└── 回顾："上次这个会讨论了什么结论"

人做决策：
├── 会议中的观点表达和谈判（Agent 不参与）
├── 纪要的准确性确认
├── 会议结论的解读和后续行动
└── 哪些会该开、哪些该取消

协作模式：Agent 是会议助理，不是参会者
```

### 4.8 审批（Approval）

```
Agent 主导：
├── 预填审批单（从 Context 里取数据）
├── 催审批（"你有 3 个审批卡了 2 天了"）
├── 审批状态追踪
└── 历史审批查询

人做决策：
├── 审批通过/拒绝（这是权责，不能委托）
├── 审批条件的判断
└── 流程例外处理

协作模式：Agent 管流程，人管决策
```

## 5. 产品架构设计

### 5.1 产品结构：三层

**第一层：我在（Presence）**

用户打开产品，看到的不是文件、不是项目、不是工具列表。看到的是**"你今天有 3 件事需要看一下"**，下面是卡片。

**第二层：我说（Expression）**

一个永远在的输入。说什么都行。Agent 听到了就去干，干完了回到第一层变成卡片。

**第三层：它们在跑（Background）**

用户看不到的层。Agent 群在 Context 里持续工作，只有需要决策时才推卡片。

### 5.2 一天的体验

```
早上打开 → "昨天有 2 封邮件需要你决策，今天有 3 个会，
           我已经帮你把下午的会材料准备好了。"

用户扫一眼 → "下午那个会改到明天"
             → Agent 去协调，通知参会人，更新材料

           → "邮件那个，第一封你直接回，第二封我看看"
             → 第一封 Agent 自动回复
             → 第二封推卡片，用户选

然后关掉 → 去干别的。Agent 继续跑。
```

用户这一天可能就**打开了两次，每次 2 分钟**。

### 5.3 企业 + 个人统一

产品可以同时服务工作和个人场景。不是两套系统，是一个系统，两套 Boundary。

```
Boundary = PersonalBoundary + EnterpriseBoundary(可选)
```

关键：**不是数据打通，是 Agent 的理解打通。** Agent 同时看到工作和生活，推理可以跨域，但数据不会泄露。

企业关心的：
- 企业数据不出去 ✅ Boundary 保证
- 员工工作效率提升 ✅ Agent 就是干这个的
- 可审计、可管控 ✅ Boundary 有 audit trail

## 6. 飞书作为基建的技术方案

### 6.1 核心思路

不替代飞书，搭在飞书上面。飞书是**能力供应商**，不是产品容器。

```
你的产品（独立 App / Web）
    │
    │ 调用 API
    ▼
飞书（能力层 + 数据层）
├── 日历          → Context: 日程数据
├── 文档/Wiki     → Context: 知识库 + 产出物
├── 消息          → Context: 沟通记录
├── 多维表格      → Context: 结构化业务数据
├── 任务          → Context: 待办和项目进度
├── 邮件          → Context: 邮件往来
├── 审批          → Action: 流程类操作
├── 视频会议      → Action: 会议安排和纪要
├── OKR           → Context: 目标和进展
└── 通讯录        → Context: 组织关系
```

### 6.2 天然优势

1. **Context 不用自己建** — 飞书已经是很多人的工作操作系统，数据已经在那
2. **Boundary 有天然载体** — Agent 能看到什么 = 用户在飞书里能看到什么
3. **Action 天然能执行** — 发消息、改日历、写文档全部通过飞书 API
4. **卡片系统现成的** — 飞书消息卡片天然就是 Card Engine
5. **企业分发零成本** — 不需要企业再采购新工具

### 6.3 技术架构

```
┌────────────────────────────────────────────┐
│               产品客户端（独立 App / Web）    │
│  ┌──────┐  ┌──────────┐  ┌──────────┐     │
│  │对话框  │  │卡片流    │  │Dashboard │     │
│  │(说)   │  │(选)      │  │(全景)    │     │
│  └───┬───┘  └────┬─────┘  └────┬─────┘     │
└──────┼──────────┼────────────┼─────────────┘
       ▼          ▼            ▼
┌────────────────────────────────────────────┐
│            Agent 服务（你的产品核心）        │
│                                            │
│  ┌───────────┐  ┌──────────┐  ┌────────┐  │
│  │Intent      │  │Agent     │  │Card    │  │
│  │Engine      │  │Runtime   │  │Engine  │  │
│  └─────┬─────┘  └────┬─────┘  └───┬────┘  │
│        └──────────────┼────────────┘       │
│                       ▼                    │
│              ┌──────────────┐              │
│              │Boundary      │              │
│              │Enforcer      │              │
│              └──────┬───────┘              │
│                     ▼                      │
│              ┌──────────────┐              │
│              │Context Store │              │
│              │(本地索引层)   │              │
│              └──────┬───────┘              │
└─────────────────────┼──────────────────────┘
                      │
                      │ 飞书 Open API
                      ▼
┌────────────────────────────────────────────┐
│               飞书平台                      │
│  日历 │ 文档 │ 消息 │ 任务 │ 邮件 │ 审批   │
└────────────────────────────────────────────┘
```

### 6.4 接入优先级

| 优先级 | 接什么 | 用户价值 |
|--------|--------|---------|
| P0 | 日历 + 消息 | "帮我看看今天有什么要处理的" |
| P0 | 文档 + Wiki | "帮我找一下上次那个方案" |
| P1 | 任务 | "帮我把会议纪要转成待办" |
| P1 | 邮件 | "帮我回复这封邮件" |
| P2 | 多维表格 | "帮我更新一下项目状态" |
| P2 | 审批 | "帮我提交这个审批" |
| P3 | OKR | "这个季度目标进展怎么样" |

## 7. 会议实时 Agent 方案

### 7.1 三种介入模式

**静默模式 — 完全后台**
- 实时转写、要点提取、实体识别、情绪信号
- 用户什么都不用做，数据在会后极其有价值

**按需模式 — 用户触发**
- 一个极轻量的触发方式（手势/按钮/语音唤醒）
- Agent 秒回：查数据、翻历史、补上下文
- 核心就是"随身带一个知道所有事的助理"

**主动模式 — 关键时刻提醒**
- 只在信息价值大于打断成本时出现
- 数据不一致、历史共识被违反、承诺被遗忘
- 提醒是静默的（屏幕上一行小字），不打断

### 7.2 会中 Agent 原则

**会中的 Agent 是隐形的。** 好的体验是：你开完会觉得"今天这个会开得很顺"，但你说不清 Agent 帮了什么。

### 7.3 速度优化方案

核心思路：**不是"搜了再想"，是"提前准备好，实时匹配"。**

**会前预加载：**
- 会议开始前 5 分钟，Agent 自动拉取相关文档、历史会议、项目数据
- 全部向量化，加载到内存中的向量索引

**会中流式处理（并行）：**
```
ASR 输出一句话
    ↓ 同时做三件事（并行，不是串行）
    ├── 向量语义匹配（5ms）
    ├── 实体提取（10ms）  
    └── 关键词触发器（1ms）
    ↓
    判断是否命中（规则匹配，1ms）
    ↓
    命中了 → 调 LLM（300-500ms）
    没命中 → 丢弃，用户无感知
```

**关键优化：80-90% 的句子直接丢弃，只有真正相关的才调 LLM。**

### 7.4 推荐技术栈（开源）

| 环节 | 推荐方案 | 延迟 |
|------|---------|------|
| ASR 语音转文字 | FunASR（阿里达摩院开源） | 200-300ms |
| LLM 推理 | vLLM + Qwen2.5-32B 或 DeepSeek API | 500-800ms |
| 向量检索 | Qdrant | < 10ms |

总延迟预算：命中时 400-600ms，不命中时 10ms。

### 8.1 Agent 框架对比

| | OpenAI Agents SDK | LangChain/LangGraph | CrewAI | Vercel AI SDK | Mastra | Pydantic AI |
|---|---|---|---|---|---|---|
| **语言** | Python | Python + JS | Python | TypeScript | TypeScript | Python |

### 8.2 各框架一句话总结

- **OpenAI Agents SDK**：最少代码跑起来，适合 MVP 和单 Agent 场景

- **Mastra**：TypeScript 全栈 Agent 框架，有内建 workflow 和 eval
- **Pydantic AI**：最轻、类型最安全，适合简单工具型 Agent

**复杂编排阶段：LangGraph**
**TypeScript 全栈：Mastra 或 Vercel AI SDK**

## 9. MVP 实现路径

### 9.1 砍掉一切，只留一个循环

```
用户说一句话 → Agent 查飞书 → 回答/执行
```

不需要 ASR，不需要会议实时分析，不需要向量数据库，不需要卡片流。

### 9.2 MVP 只做三件事

1. **一个聊天界面** — 最简：Web 页面，一个输入框，一个消息列表
2. **一个后端服务** — LLM + function calling 循环
3. **接三个飞书 API** — 日历、任务、消息搜索

### 9.3 代码量估算

```
后端核心逻辑：~300 行 Python
飞书 API 封装：~200 行（三个接口）
Tool 定义：~100 行
前端聊天页面：~200 行 HTML/JS
────────────────────────
总计：~800 行
```

### 9.4 技术栈

```
后端：Python + OpenAI Agents SDK（或 LangChain）
LLM：DeepSeek API 或 Qwen（DashScope）
飞书：lark-cli / 飞书 Open API
前端：最简 HTML + SSE 流式输出
部署：一台服务器
```

### 9.5 用 OpenAI Agents SDK 的核心代码骨架

```python
from agents import Agent, Runner, function_tool

@function_tool
def search_calendar(start_date: str, end_date: str) -> str:
    """查询飞书日历中的日程"""
    # 调飞书 API
    return calendar_results

@function_tool
def search_tasks(status: str = "todo") -> str:
    """查询飞书任务"""
    return task_results

@function_tool

    """搜索飞书消息"""
```

## 10. Demo 内核方案

### 10.1 Claude Code 不开源

Claude Code 是 Anthropic 的闭源产品。2026 年 3 月 31 日 Anthropic 曾意外在 npm 包中暴露了源码（51.2 万行），但随后发了 DMCA takedown，公开仓库已被移除。

**不能直接用 Claude Code 源码。需要找开源替代方案。**

### 10.2 Claude Code 的架构（从泄露源码可知）

- **单线程主循环**：模型分析 → 产生消息/工具调用 → 执行 → 结果回模型 → 循环
- **子 Agent**：独立上下文窗口、独立工具集、独立权限模式，避免主对话被中间步骤污染
- **权限系统**：工具分层审批，可配置自动批准特定工具
- **工具集**：read / write / edit / bash / grep / find / web_search / web_fetch

### 10.3 开源替代方案对比

| 项目 | 语言 | GitHub Stars | 核心特性 | Agent Loop | 子 Agent | 工具系统 | 适合做 Demo 内核？ |
|------|------|-------------|---------|-----------|---------|---------|------------------|
| **Cline** | TypeScript | 40k+ | SDK 分层架构（@cline/agents + @cline/core + @cline/llms），Plan & Act 循环，MCP 支持 | ✅ | ✅ 只读研究子 Agent | ✅ 完整工具集 | ⭐⭐⭐ 最推荐 |
| **OpenCode** | Go | 30k+ | 终端原生，Agent Teams（lead + teammates），消息传递协作，SQLite 会话管理 | ✅ | ✅ 进程内消息传递 | ✅ 文件/Shell/Web | ⭐⭐ Go 生态对接飞书稍麻烦 |

| **Goose** | Rust | 20k+ | MCP/ACP 协议，子 Agent 并行，安全沙箱，通用 Agent | ✅ | ✅ 独立子 Agent | ✅ 70+ MCP 扩展 | ⭐⭐ Rust 生态门槛高 |

### 10.4 推荐方案：Cline SDK

**推荐用 Cline 的 SDK 作为 Demo 内核。** 理由：

1. **TypeScript** — 飞书 SDK 也是 TypeScript，生态对接无缝
2. **SDK 分层架构** — `@cline/agents`（无状态 Agent 循环）+ `@cline/core`（有状态编排）+ `@cline/llms`（模型抽象），可以只取 Agent 循环层
3. **子 Agent 系统** — 内建只读研究子 Agent，可扩展为 explore/worker/reviewer
4. **Plan & Act 模式** — 先规划再执行，符合协作理念
5. **MCP 支持** — 飞书 API 可封装为 MCP tool，天然兼容
6. **模型无关** — 不绑死 Claude，可接 DeepSeek/Qwen

### 10.5 具体改造方案

```
保留 Cline SDK 的：
├── Agent Loop（@cline/agents 的无状态循环）
├── 子 Agent 机制（扩展为 explore/worker/reviewer）
├── 工具系统框架（tool 注册 + 调用机制）
└── 会话管理（@cline/core 的 session lifecycle）

替换为我们的：
├── 工具集 → 飞书 API tools（日历/文档/消息/任务）
├── 交互层 → Web 对话框 + 卡片流（替代 VS Code 面板）
├── Context Store → 飞书数据 + 本地向量索引
└── 权限模型 → Boundary Enforcer（个人 + 企业策略）
```
